## Housekeeping

## Issue references

Issues live in two repos: `flolec31/stencilia-product` (product/epic level) and `flolec31/stencilia-back` (backend). **Every backend change references a stencilia-back issue**, never a product issue directly. When a product issue needs backend work, create a matching **daughter** issue in stencilia-back and attach it to the parent as a native GitHub **sub-issue** (cross-repo sub-issues are supported within the owner), so the parent/child hierarchy is real GitHub metadata, not body text; if front-end work is also needed, a sibling daughter is created in the front repo too. Wiring a sub-issue is a REST call on the **parent**: `gh api --method POST repos/flolec31/stencilia-product/issues/<parentNo>/sub_issues -F sub_issue_id=<childDbId>` where `<childDbId>` is the daughter's internal id (`gh api repos/flolec31/stencilia-back/issues/<childNo> --jq .id`), not its issue number.

Why: GitHub's bare `#N` is repo-local (in a stencilia-back commit/PR, `#2` means back#2, not product#2), and closing keywords (`Closes #N`) only auto-close issues in the **same** repo — cross-repo auto-close is never honored. Routing every backend change through a local daughter means the existing `type(#N): subject (#PR)` commit convention (where `#N` is the stencilia-back issue) keeps working unchanged, and `Closes #N` on the PR still auto-closes on merge. Use a fully-qualified `owner/repo#N` only to *link* across repos, never expecting it to close anything. Branch names use the back issue number too (e.g. `fix/81-...`).

## Commands

```bash
# Build
./gradlew build

# After adding, removing, or updating any dependency (including plugins):
# regenerate dependency verification checksums, otherwise CI will fail
./gradlew --write-verification-metadata sha256 --refresh-dependencies dependencies buildEnvironment

# Run tests
./gradlew test

# Run a single test class
./gradlew test --tests "com.stencilia.stenciliaback.SomeTest"

# Run the app locally (with Testcontainers instead of Docker Compose)
./gradlew bootRun --args='--spring.profiles.active=test'
# Or via the test main entry point:
./gradlew bootTestRun
```

> **⚠️ Agents/Claude: never run the app (`bootRun`, `bootTestRun`, or any task that boots Spring) — only the human does.**
> A plain `bootRun` boots against the developer's **persistent local Postgres** (via `spring-boot-docker-compose`) and **applies Liquibase migrations** to it. If a changeset is later edited (which is normal on an in-progress feature branch), Liquibase then fails startup with a checksum-mismatch (`ValidationFailedException`) because the stored checksum no longer matches the edited file. Agents must verify work with `./gradlew test`/`build` (Testcontainers, ephemeral DB) only. These app-run tasks are hard-denied in `.claude/settings.json`.

## Architecture

This is a Spring Boot application using Kotlin + Spring Boot 4 + Java 24 + Gradle (Kotlin DSL).

**Key stack choices:**
- **Spring Data JPA** with PostgreSQL at runtime.
- **Liquibase** for database migrations — changesets live under `src/main/resources/db/changelog/`, one folder per feature branch (e.g. `1-tattoo-artist-registration-email-validation/`), SQL format.
- **Spring Security** — all endpoints secured by default; `SecurityConfig` permits `/auth/**` (which covers both `/auth/artist/*` and `/auth/client/*`), `/swagger-ui/**`, `/v3/api-docs/**`, `GET /actuator/health` + `GET /actuator/health/**` (public so a VPS/Docker/reverse-proxy healthcheck or liveness/readiness probe isn't blocked by the `ROLE_ARTIST` catch-all — actuator exposes only `health` over the web by default, so the `/health/**` wildcard opens nothing else), `GET /appointment/verify`, `POST /appointment/{slug}`, `POST /appointment/{slug}/reference` and `POST /appointment/{slug}/links` (public client-facing endpoints). `POST /auth/artist/change-password` is the one exception carved out of that space — its `.hasRole("ARTIST")` matcher is registered *before* the `/auth/**` `permitAll()` matcher, since Spring Security's `authorizeHttpRequests` uses first-match-wins ordering. `GET /client/appointment/{appointmentId}` and `GET /client/appointment/{appointmentId}/messages` are each declared with `.hasRole("CLIENT")` *before* the `anyRequest().hasRole("ARTIST")` catch-all (same first-match-wins reason); note the `/messages` sub-path needs its own matcher because a `{appointmentId}` path variable only matches a single segment. Always scope `permitAll()` with `HttpMethod` when the route has an authenticated sibling. `/actuator/prometheus` is **not** on the JWT chain at all: a separate `@Order(1)` `SecurityFilterChain` (`securityMatcher("/actuator/prometheus")`, HTTP Basic, stateless) guards it with an in-memory scrape credential from `app.metrics.username`/`password` (env `APP_METRICS_USERNAME`/`APP_METRICS_PASSWORD`); blank credential → no user created → endpoint locked (401 for everyone). Never `permitAll` it. Enabling the registry needs `management.prometheus.metrics.export.enabled: true` in `application.yaml` (Spring Boot 4 treats `management.defaults.metrics.export.enabled` as false by default, so `micrometer-registry-prometheus` + exposure alone 404s); the same `management` block is mirrored in `src/test/resources/application.yaml` since the test classpath shadows main.
- **RBAC** — every JWT carries a `type` claim (`artist` or `client`, see the `Role` enum in `auth`). The `JwtAuthenticationConverter` bean in `SecurityConfig` maps that claim to a single `ROLE_ARTIST`/`ROLE_CLIENT` `GrantedAuthority`; artist-only routes are declared with `.hasRole("ARTIST")` (e.g. `GET /artists/me`, `POST /auth/artist/change-password`, and the catch-all `anyRequest()`).
- **JWT authentication** (`spring-boot-starter-oauth2-resource-server`) — stateless, HMAC-SHA256. Access tokens (15 min) issued as JWTs for both artists and clients. Refresh tokens are opaque UUIDs stored in a single unified `refresh_token` table (columns: `token` PK, `subject_id`, `subject_type` — no FK, since the subject can be either a `TattooArtist` or `TattooClient`). Refresh-token lifecycle (issue/rotate-on-refresh/revoke/revoke-all) is centralized in `RefreshTokenService`, shared by artist and client auth; refresh tokens live 30 days for artists, 48 hours for clients. `JwtConfig` binds `app.jwt.secret` (env: `APP_JWT_SECRET`, min 256-bit base64) and `app.jwt.access-token-expiry`. `JwtServiceImpl` uses `NimbusJwtEncoder` with an explicit `JwsHeader.with(MacAlgorithm.HS256)` — required for Nimbus key selection. `JwtAuthenticationEntryPoint` must be registered on **both** `exceptionHandling` and `oauth2ResourceServer` DSL blocks to cover both missing-token and invalid-token paths.
- **springdoc-openapi** (`springdoc-openapi-starter-webmvc-ui`) for Swagger UI at `/swagger-ui.html`.
- **Resend** (`resend-java`) for transactional email via `EmailServiceImpl`. API key configured via `application.yaml` (bound with `@ConfigurationProperties` in `ResendConfig`).
- **RestClient** (not WebClient/RestTemplate) for outbound HTTP calls.
- **Spring application events** for decoupling, named as **domain facts** (past tense, declarative — `ArtistVerifiedEvent`, `AppointmentRequestVerifiedEvent`, `SupportMessageSubmittedEvent`), **not** as command/"please-send-this-email" requests. A publisher announces one fact; any number of `@TransactionalEventListener(AFTER_COMMIT)` listeners react (`EmailEventListener` sends mail, `AdminAlertEventListener` alerts the admin — see "Analytics & alerting"). Adding a reaction means adding a listener, never editing the publisher. The `Event` suffix is the convention for these fact events; two genuinely user-initiated requests keep a `…Requested` name because they *are* facts about a user action, not email commands (`AppointmentLinksRequested`, `ClientAccessCodeRequested`).

**Package structure** (under `com.stencilia.stenciliaback`):
- `artist` — `TattooArtist` entity, repository, service, profile photo upload
- `appointment` — `Appointment` entity, repository; service and controller are split by audience: `*Submission*` (public client form submission, reference upload, email verification, and link retrieval), `*Management*` (JWT-protected artist views: two batched request feeds plus details, archive/unarchive/mark-new), and `*Client*` (`AppointmentClientController` at `GET /client/appointment/{appointmentId}`, `ROLE_CLIENT`, client id from the JWT subject — lets an authenticated client read their own appointment). The client read returns `ClientAppointmentDetailsResponseDto`, a trimmed variant of the artist `AppointmentDetailsResponseDto`: it drops the artist-inbox fields (`new`, `archived`) and swaps `clientName` for `artistName`, and unlike the artist read it has **no** `new`-flip side effect. Ownership is enforced by `AppointmentAccessService.findAppointmentForClient(clientId, appointmentId)`, which throws `AppointmentNotFoundException` (404) both when the appointment is missing/unverified **and** when it belongs to another client (no existence leak), in contrast to the artist-side `findOwnedAppointment` which returns 403 for a wrong-owner match. Link retrieval (`POST /appointment/{slug}/links`, body `{ email }`) lets a client who lost their access link(s) request them by email: it returns `204` **regardless** of whether a match exists (enumeration protection), and only when the client has verified appointments with that artist (archived included) does it publish `AppointmentLinksRequested`, emailing one link per appointment (`{baseUrl}/appointment/{id}`, labeled by submission date `dd/MM/yy` + tattoo description). No rate-limiting yet — noted as future work. **Unread-messages flag**: an `unreadMessages` boolean marks whether a thread has messages the *viewer* hasn't opened yet (a `Message` with `read_at IS NULL` from the counterpart sender — see the `discussion` read-tracking note). It appears on three DTOs, always computed from the viewer's perspective:
  - `AppointmentItemResponseDto` (artist request feeds): `true` when ≥1 `CLIENT` message is unread. The artist's requests are served as two independent batched feeds (20/page, `page` is the only client-controlled knob, size fixed server-side): `GET /appointment/inbox` (non-archived, ordered new first, then requests with an unread client message, then most recently verified, with id as a stable tiebreaker) and `GET /appointment/archive` (archived only, most recently verified first). The inbox ordering and the optional filters are computed in SQL by `AppointmentRepository.findInbox` via a correlated `EXISTS` over the message table, so both apply across the artist's whole request set, not just a loaded page; the archive uses a derived query (`...AndArchivedTrueOrderByVerifiedAtDescIdAsc`). The inbox filters are two independent boolean query params `new` and `unread` (default false), OR-combined when both set (`?new=true&unread=true` = new or has-unread; neither = all) — passed straight through to `findInbox(filterNew, filterUnread)`, no enum/wrapper. `page` is validated with `@PositiveOrZero` (the controller is `@Validated`), so a negative page is a 400 via `GlobalControllerAdvice` rather than a 500. Both feeds map the page to DTOs through `AppointmentManagementServiceImpl.mapWithUnreadFlag`, which sets the displayed `unreadMessages` flag for the whole page with a single batched projection query (`MessageRepository.findAppointmentIdsWithUnreadFrom(ids, CLIENT)`, guarded against an empty page) rather than N+1.
  - `AppointmentDetailsResponseDto` (artist detail): same `CLIENT`-unread meaning, computed per-appointment via `messageRepository.existsByAppointmentIdAndSenderAndReadAtIsNull(id, CLIENT)`. Note the artist detail read still flips `new`→false but does **not** mark messages read (only `GET .../messages` does), so `unreadMessages` is a pre-open snapshot.
  - `ClientAppointmentDetailsResponseDto` (client detail): mirror — `true` when ≥1 `ARTIST` message is unread (`existsByAppointmentIdAndSenderAndReadAtIsNull(id, ARTIST)`). There is no client *list* (a client opens only their one appointment), so the flag lives only on the detail here.
  These reads are the `appointment → discussion` dependency (both management + client services inject `MessageRepository`); all are plain reads.
  - Resend templates only substitute string/number variables (no loops/arrays), so the variable-length list is pre-rendered in `EmailServiceImpl` into a single HTML `<ul>` string and injected via the triple-brace `{{{APPOINTMENTS_HTML}}}` variable (raw HTML); the client-supplied tattoo description is truncated to 100 chars (with `...`), wrapped in guillemets, then HTML-escaped. Template `retrieve-appointment-links` variables: `ARTIST_NAME`, `CLIENT_FIRSTNAME`, `APPOINTMENTS_HTML`.
  - Verifying an appointment (`GET /appointment/verify`) publishes one fact event `AppointmentRequestVerifiedEvent(appointment)`; `EmailEventListener` reacts by sending both the artist notification and the client confirmation (which gives them their access link `{baseUrl}/appointment/{id}`), and `AdminAlertEventListener` reacts with the admin alert. (Submission publishes `AppointmentRequestSubmittedEvent(appointment)` → the client "verify your request" email.) Client confirmation template `confirm-client-appointment-request` variables: `LINK`, `ARTIST_NAME`, `CLIENT_FIRSTNAME`.
- `auth` — root holds genuinely shared code: `JwtService`/`JwtServiceImpl`, `RefreshTokenService`/`RefreshTokenServiceImpl` (unified issue/rotate/revoke for both audiences), `RefreshToken` entity + repository, `LoginResponseDto`, shared token exceptions (`TokenNotFoundException`, `TokenExpiredException`, `InvalidRefreshTokenException`) in `auth.exception`, and `auth.controller.AuthControllerAdvice` which maps those shared exceptions (thrown by both artist and client flows). Everything artist-specific lives under `auth.artist.**`: `ArtistAuthController` (`@RequestMapping("/auth/artist")`, endpoints at `/auth/artist/{register,verify,resend-verification,login,refresh,logout,forgot-password,reset-password,change-password}`), `ArtistAuthControllerAdvice` (artist-specific exceptions only), `AuthService`/`AuthServiceImpl`, `VerificationToken`/`PasswordResetToken` entities + repositories, artist DTOs, artist fact events (`ArtistVerificationRequestedEvent`, `ArtistVerifiedEvent`, `PasswordResetRequestedEvent`, `PasswordChangedEvent`), and artist-specific exceptions (`EmailAlreadyRegisteredException`, `InvalidCredentialsException`, `AccountNotActivatedException`) in `auth.artist.exception`. Client-facing auth lives under `auth.client.**`: `ClientAuthController` (`@RequestMapping("/auth/client")`) exposes three endpoints. `POST /auth/client/request-code` (body `{ appointmentId }`) resolves the appointment to its client and issues a 6-digit `ClientAccessCode` (table `client_access_code`, PK `client_id`, 10-min expiry via `expiresAt`) using `SecureRandom`, publishing `ClientAccessCodeRequested` to email the code (template `verify-client-access-code`, variables `CLIENT_FIRSTNAME`/`CODE`); it always returns `204`, even for an unknown `appointmentId` (enumeration-safe, no email sent). Resend/brute-force is throttled so the attempt cap can't be reset by re-requesting: a **fresh** code (with `attempts` reset to 0) is minted only when no code exists or the previous one has expired; while a code is still valid, re-requesting re-sends the **same** code and never resets `attempts`, and the email is throttled to once per 60s via `last_sent_at` (`RESEND_COOLDOWN`) — a request inside the cooldown returns `204` without emailing. Net effect: at most 5 guesses per 10-min code lifetime, and at most one email per 60s. `POST /auth/client/verify-code` (body `{ appointmentId, code }`) checks the code against `ClientAccessCode`, enforcing a 10-minute expiry and a max of 5 attempts (the row is deleted once expired, exhausted, or successfully consumed) — on success it issues `{ accessToken, refreshToken }` via `RefreshTokenService.issue(clientId, Role.CLIENT)`; any failure throws `InvalidCodeException` (mapped to 401 by `ClientAuthControllerAdvice`). The `attempts` read-modify-write is guarded by a JPA `@Version` optimistic lock (column `version`) so concurrent wrong-guess requests can't race past the cap. `POST /auth/client/refresh` (body `{ refreshToken }`) rotates it via `RefreshTokenService.rotate` and returns a new pair. There is deliberately no client logout endpoint — clients have no account UI, so a refresh token is simply left to expire (48h); add a logout route only if/when a client-facing "sign out" affordance exists.
- `client` — `TattooClient` entity, repository, service (created implicitly on appointment submission)
- `common` — global exception handling (`GlobalControllerAdvice` for cross-cutting exceptions: bean-validation, upload-size, and `EmailDeliveryException`; `AbstractControllerAdvice` base), shared pagination DTO
- `discussion` — `Message` entity/`MessageSender` enum, repository, service, controller: JWT-protected appointment-scoped message thread. Split by audience like `appointment`, but the two service impls share one `DiscussionService` interface and an `AbstractDiscussionService` base (template method) that owns the audience-agnostic mechanics (normalize + `messages/{subjectId}/` prefix guard + save + signed-URL mapping); each concrete impl supplies only the three things that differ — how a `subjectId` is authorized against the appointment (`resolveAppointment`), which `MessageSender` it stamps, and which email event it publishes (`onMessagePosted`). Because two beans implement `DiscussionService`, each controller injects the interface typed as `DiscussionService` but disambiguated with `@Qualifier("discussionServiceImpl")` / `@Qualifier("discussionClientServiceImpl")` (the beans' default names). The artist side (`DiscussionController` → `DiscussionServiceImpl`) exposes `GET`/`POST /appointment/{appointmentId}/messages` (ownership via `AppointmentAccessService.findOwnedAppointment`, 403 on wrong owner); the client side (`DiscussionClientController` → `DiscussionClientServiceImpl` at `/client/appointment/{appointmentId}/messages`, `ROLE_CLIENT`, client id from the JWT subject) mirrors it for a client's own thread, ownership via `AppointmentAccessService.findAppointmentForClient` (404 no existence leak, and unverified appointments 404 — vs the artist side's 403). Both sides expose the same trio: `GET .../messages`, `POST .../messages` (send), and `POST .../messages/image` (multipart, field `image`). Reads reuse the same `MessageResponseDto` (it carries no artist-only fields — `id`, `sender`, `content`, `imageUrl`, `sentAt`, `readAt`) and the same `messageRepository.findByAppointmentIdOrderBySentAtAsc` + signed-URL mapping. **Read-tracking**: a `GET .../messages` fetch stamps `readAt = now` on the *counterpart's* still-unread messages (artist fetch marks `CLIENT` messages read; client fetch marks `ARTIST`), so each `Message.readAt` records when the recipient opened the thread. This lives once in `AbstractDiscussionService.getMessages` — the loaded entities are mutated in place and flushed by JPA dirty-checking, which is why `getMessages` is now annotated `@Transactional` (read-write, overriding the class-level `readOnly = true`); the side to mark is derived from each impl's own `sender` via the private `counterpartSender`. The `read_at` column already existed (changeset `48-discussion-tab`), so no migration was needed — this is just the write path that was never wired up. A message carries text, an image, or both (at least one required). Sending stays JSON (`{ content?, imageKey? }`); the image is uploaded first via the multipart endpoint which returns a `messages/{subjectId}/{uuid}` key (`subjectId` = the caller's artist or client id — `ImageUploadService.uploadMessageImage`'s id param is just the middle path segment). Each side guards that a supplied `imageKey` is prefixed with the caller's own `messages/{subjectId}/` (else `InvalidMessageImageKeyException` → 400, message audience-neutral "does not belong to you"). Image URLs are returned as 1h presigned URLs on read. Posting sets `sender` per side (`ARTIST`/`CLIENT`) and publishes a side-specific fact event: artist posts → `ArtistMessagePostedEvent` → `sendNewMessageEmailToClient` (template `notify-client-new-message`, vars `LINK`/`ARTIST_NAME`/`CLIENT_FIRSTNAME`); client posts → `ClientMessagePostedEvent` → `sendNewMessageEmailToArtist` (template `notify-artist-new-message`, vars `LINK`/`ARTIST_NAME` = artist's `artistName`/`CLIENT_NAME` = client full name). Neither notification includes message content. The client-notify email's `LINK` points to the client's appointment page (`{baseUrl}/appointment/{id}`, built by the shared `clientAppointmentLink` helper — same link as the appointment-request confirmation email); the artist-notify email's `LINK` points to the artist dashboard (`{baseUrl}/dashboard`, built by the shared `artistDashboardLink` helper — same link as the new-appointment notification email, since no per-appointment artist deep link exists yet).
- `email` — `EmailService`, Resend client, event listener
- `security` — `SecurityConfig`, password encoder
- `storage` — `StorageService` / `StorageServiceImpl` — S3-compatible file storage via AWS SDK v2; `ImageValidator` — single source of truth for image validation (JPEG/PNG/WebP, max 5 MB), used by every image entry point (references, support screenshots, message images, and the artist profile photo in `TattooArtistServiceImpl`); `ImageUploadService` — shared validate-and-upload logic (delegates validation to `ImageValidator`, then key-prefixes and stores) used by appointment reference, support screenshot, and message image uploads (prefixes `references/`, `contact-screenshots/`, `messages/`)
- `metrics` — on-demand admin metrics (back #85). `MetricsRegistrar` (`@PostConstruct`) registers eight Micrometer gauges backed by live SQL (`MetricsRepository`, a `JpaRepository<TattooArtist>` hosting cross-entity `@Query` counts; all exclude `test_account` emails), evaluated at scrape time and exposed on the secured `/actuator/prometheus` (see SecurityConfig) for a VPS push agent → Grafana Cloud (ops, not in this repo). Gauge ids: `stencilia.artists.registered`/`.active`, `stencilia.requests.counted`/`.submitted`/`.validated`/`.lost.unvalidated`/`.lost.unopened`, `stencilia.visits` (named `.visits` not `.visits.total` — Micrometer strips the `_total` suffix from gauges). "Counted" (client email ≠ artist email) applies only to `.counted`/`.active`; `.submitted`/`.validated`/`.lost.*` count validated/submitted requests broadly. `countLostUnopened` and `sumVisits` are native SQL (`new` is a JPQL keyword; Postgres `SUM(bigint)` needs `CAST(... AS bigint)` to coerce to `Long`). Public-page visits are counted cookielessly on `GET /artists/{slug}`: `TattooArtistServiceImpl.getProfileBySlug` (the controller delegates only to its own service) calls `PageVisitService.recordVisit(artistId)`, which does an atomic upsert into `page_visit_count` (per-artist integer, PK `artist_id`) in a `REQUIRES_NEW` transaction (the profile read is `readOnly`), swallowing failures. The backend counts **every** hit to the public slug and does **not** inspect identity: on this public endpoint the frontend sends no JWT, so there's no reliable signal, and no cookie is allowed. Excluding an artist's own views is handled on the frontend instead — an authenticated artist's "my page" uses an authed path, not the public slug URL (`flolec31/stencilia-product#11`) — so a connected artist checking their profile never hits this endpoint.
- `support` — `SupportMessage` entity/enum, repository, service, controller: artist-submitted contact/support messages (bug/help/idea/other), with optional screenshot via `storage.ImageUploadService`. Submitting publishes one fact event `SupportMessageSubmittedEvent(supportMessage)`; `EmailEventListener` reacts by notifying `app.support.notification-email` (env `APP_SUPPORT_NOTIFICATION_EMAIL`) and confirming receipt to the submitting artist, and `AdminAlertEventListener` reacts with the admin alert.

**Testing approach:**
- Tests use Testcontainers for PostgreSQL **and an S3-compatible store** (`adobe/s3mock`, pinned tag) via `TestcontainersConfiguration` (in `src/test`), imported with `@Import(TestcontainersConfiguration::class)`. s3mock runs as a `GenericContainer` (no dedicated Testcontainers module) on port 9090; the `stencilia` bucket is created via the AWS SDK, and endpoint/access-key/secret-key are injected via `DynamicPropertyRegistry` (also exposed as `s3Endpoint`/`s3AccessKey`/`s3SecretKey` for tests that build their own `S3Client`). Any credentials are accepted.
- `TestStenciliaBackApplication` allows running the full app locally with Testcontainers in place of a real database.
- Integration tests use `@SpringBootTest` + `@AutoConfigureMockMvc`; external services (e.g. `EmailService`) are `@MockitoBean`.
- Docker Compose (`compose.yaml`) runs Postgres 17 + `adobe/s3mock` for manual dev; not used in tests. s3mock's port 9090 is mapped to host 9000 so `application-local.yaml`'s `http://localhost:9000` endpoint is unchanged, and `COM_ADOBE_TESTING_S3MOCK_STORE_INITIAL_BUCKETS=stencilia` auto-creates the bucket on startup. For local persistence, s3mock stores to `/data` (`COM_ADOBE_TESTING_S3MOCK_STORE_ROOT`) with `COM_ADOBE_TESTING_S3MOCK_STORE_RETAIN_FILES_ON_EXIT=true`, backed by the named volume `s3mock-data` — without these, s3mock defaults to an ephemeral temp dir wiped on container restart. The service also runs `user: "0:0"` (root): the named volume is root-owned when Docker first creates it, and s3mock's default uid (1000) otherwise can't write its store, so every `putObject` fails with a 500. The Testcontainers s3mock stays ephemeral (no volume/retention) by design.

**Kotlin compiler flags:**
- `-Xjsr305=strict`: null-safety annotations from Java are treated as strict.
- `-Xannotation-default-target=param-property`: annotations on constructor parameters apply to both the parameter and the backing property (important for JPA/Jackson).

**Kotlin conventions:**
- Use the `$$` string prefix for `@Value` annotations to avoid escaping `$`: `@Value($$"${some.property}")` not `@Value("\${some.property}")`.

**Input length limits** — every free-text request field and every list has a server-enforced max via bean validation (`@Size`), so an over-long value is a `400` (Spring's default bean-validation response), never a truncation or a server error, and never exceeds the backing column. Default categories: names 100, emails 254, single-line short texts 255, multi-line long texts 2000, lists capped per endpoint (references max 10); fields with a stricter format rule (slug, 6-digit access code, password) keep it, and passwords additionally cap at 72 so an over-72-byte value is a clean `400` rather than a BCrypt error. Server-issued identifiers replayed by the client (storage keys, reset token) are bounded to their column capacity; opaque UUID tokens (refresh tokens, verify token) are not length-constrained because a bad value is already rejected cleanly. The full per-field inventory is maintained on back issue #78.

**JPA entities** must be in classes annotated with `@Entity`, `@MappedSuperclass`, or `@Embeddable` — the `allOpen` plugin makes these open automatically so JPA proxying works without `open` keywords.

## Analytics & alerting

Architecture spec: `docs/superpowers/specs/2026-11-20-analytics-alerting-architecture-design.md`; the product-event-alerts implementation design: `docs/superpowers/specs/2026-11-20-product-event-alerts-design.md`. The epic (product #4) splits into product-event alerts (#5, back #83 — **done**), on-demand metrics (back #85 — **backend done**, see the `metrics` package; Grafana Cloud + push agent are VPS ops still to do), and technical/break alerts (#7). Alerts reach the admin's phone via **Telegram**; metrics (later) go to Grafana Cloud via a push agent. A monitoring/alerting failure must never block or slow a user flow, and no end-client PII ever leaves the DB (alerts carry slug/type only).

- **`alert` package** — the reusable **notification core** (used by #5 now, #7 later). `AdminAlertService`/`AdminAlertServiceImpl` posts to the Telegram Bot API (`sendMessage`) via **RestClient**; `send` is `@Async` (app-level `@EnableAsync` lives on `StenciliaBackApplication`) and wraps everything in try/catch that only logs, so a Telegram outage neither propagates nor runs on the request thread. Bot token + chat id bind from `app.telegram.*` (`APP_TELEGRAM_BOT_TOKEN`, `APP_TELEGRAM_CHAT_ID`, both default empty → `send` no-ops when unset). `TelegramConfig` is a `@ConfigurationProperties("app.telegram")`.
- **Three product-event alerts (#5).** `AdminAlertEventListener` has three `@TransactionalEventListener(AFTER_COMMIT)` methods, mirroring `EmailEventListener`; each filters test accounts, formats a one-line PII-free message, and calls `AdminAlertService.send` inside a `runCatching`. The domain services publish plain business-fact events (they stay ignorant of Telegram and of the test-account rule):
  - artist verifies email → `ArtistVerifiedEvent(slug, email)` in `AuthServiceImpl.verify` (fires on verification, not registration; the single-use verification token guarantees one alert per sign-up). Message `🎨 New artist signed up — {slug}`.
  - client verifies their request → `AppointmentRequestVerifiedEvent(appointment)` in `AppointmentSubmissionServiceImpl.verify`, inside the `verifiedAt == null` idempotent block (re-clicking the link → no second alert, relies on back #81); the alert listener reads `appointment.artist.slug` + filters on **both** `appointment.client.email` **and** `appointment.artist.email` (BR-5: either being a test account suppresses the alert). Message `📋 New tattoo request — {slug}` (admin-facing "request" language; at this stage it's a *request*, not a booked appointment — hence the event names the request, not the appointment). A self-request (client email == artist email) still alerts unless that email is a test account.
  - artist sends support → `SupportMessageSubmittedEvent(supportMessage)` in `SupportMessageServiceImpl.submit`; the alert listener reads `supportMessage.artist.email` (filter) + `.artist.slug` + `.type`. Message `🛟 Support ({TYPE}) — {slug}` (`SupportMessageType.name`); never the message content.
- **Test accounts** — `test_account` table (email PK) + `TestAccount` entity + `TestAccountRepository.existsByEmailIgnoreCase` (case-insensitive match). Emails listed here fire **no product alert** (and later count in no metric, #6); technical alerts (#7) will still apply to them. The list is edited **directly in the DB** — deliberately no `ROLE_ADMIN`/admin UI (the architecture avoids an app-side admin role; the admin identity is the Telegram chat + the DB). "Excluded" is used only in prose/comments where the context is explicit, never as a bare identifier.
- **Technical break alerts (#7, back #87 — in-app slice).** Two direct-push triggers reuse the same `AdminAlertService`, both PII-free, neither filtering test accounts (BR-5: technical alerts fire even for test accounts):
  - **Email-send failure (BR-1b):** `ResendEmailClient.sendEmail`'s catch block calls `adminAlertService.send("✉️ Email failed to send — type: {templateId}")` before rethrowing `EmailDeliveryException`. Carries the template id (the email *type*) only, never the recipient. This is the dependable seam because every email is sent from an `@TransactionalEventListener(AFTER_COMMIT)` listener, where a thrown `EmailDeliveryException` is logged-and-swallowed by Spring and never reaches a `@ControllerAdvice`.
  - **Every server 5xx (BR-1c):** `common.UnhandledExceptionAdvice` — a `@RestControllerAdvice @Order(LOWEST_PRECEDENCE)` extending `ResponseEntityExceptionHandler`, whose fallback `@ExceptionHandler(Exception)` returns 500 and sends `"💥 500 on {method} {requestURI}: {exceptionSimpleName}"` (path only, no query string — it may hold a token). Extending `ResponseEntityExceptionHandler` is load-bearing: its inherited handlers keep Spring's framework exceptions (404/405/415/400 malformed/400 validation) as their proper 4xx so bot/user errors never alert (BR-4); a bare `@ExceptionHandler(Exception)` would turn a bot's 404 into an alerted 500. Security-layer 4xx (401/403 from the entry point) short-circuit before the dispatcher and never reach the advice.
  - **Advice ordering invariant:** every domain-specific advice extends `common.AbstractControllerAdvice`, which now implements `Ordered` at `HIGHEST_PRECEDENCE` so the specific handlers always outrank the lowest-precedence `UnhandledExceptionAdvice`. Without this they default to `LOWEST_PRECEDENCE` and **tie** with the catch-all (same cross-bean first-match-wins gotcha), letting it preempt a specific 4xx handler and 500 it. New cross-cutting advices should extend `AbstractControllerAdvice`.
  - **No double-alert:** the two seams are disjoint — `EmailDeliveryException` has a specific 503 handler in `GlobalControllerAdvice` (a domain advice, so higher precedence) and never reaches the catch-all, so a failed email alerts exactly once (at its source).
  - The rest of #7 (reachability, resource >90%, backup failure/staleness — BR-1a/d/e/f) is **Grafana-Cloud alert rules + a VPS push agent**, an ops runbook in the design spec, **not** app code.
  - **Dashboard, push agent, and alert rules live in a separate `stencilia-monitoring` repo, not here.** That repo holds the Grafana dashboard (the `stencilia_*` gauges plus a Health section: reachability, 5xx, JVM/CPU/DB-pool, host disk/memory, backup freshness), the Grafana Alloy config that scrapes this app's `/actuator/prometheus` + host metrics (via Alloy's embedded unix exporter) + backup timestamps (textfile written by the stencilia-backup jobs) and `remote_write`s to Grafana Cloud, and the Prometheus-format alert rules routed to Telegram. This backend repo only exposes the metrics on `/actuator/prometheus`; collection, dashboards, and alerting all live in stencilia-monitoring.

## Deployment

Containerised via `Dockerfile` (`eclipse-temurin:24-jre-alpine`, runs the boot jar built by CI). Deployed to a VPS as two containers — `stencilia-back` + a tunnel-based reverse proxy that fronts the HTTP API; the app has no published ports. Production Postgres and object storage are **external managed services**, reached via env vars. There is **no prod Spring profile**: the container runs the default profile and binds everything from env (datasource via `SPRING_DATASOURCE_URL/USERNAME/PASSWORD` — *not* `DB_*`; `APP_JWT_SECRET` is required or the app won't boot). The deployed container must stay healthy against `/actuator/health` (public — see SecurityConfig), which is also the Docker `healthcheck` and the deploy gate.

- CI/CD is three separate workflows under `.github/workflows/`: `ci.yml` (test + Sonar on PRs), `publish.yml` (**Build & publish image** — on push to `main`, builds + pushes `ghcr.io/flolec31/stencilia-back:main` + `:sha-<sha>` to private GHCR), and `deploy.yml` (**Deploy to VPS** — manual `workflow_dispatch`, input `tag` default `main`; use `sha-<sha>` to pin/roll back). The deploy SSHes to the VPS, logs in to GHCR with the job's short-lived token piped over stdin (no long-lived registry secret on the box), rewrites `IMAGE_TAG` in `~/app/.env`, `docker compose pull && up -d`, and waits for the healthcheck. Build and deploy are deliberately split (different triggers/permissions/purpose).
- Secrets/vars: `VPS_SSH_KEY` + `VPS_KNOWN_HOSTS` (secrets), `VPS_HOST` + `VPS_USER` (vars).
- The VPS's `~/app/docker-compose.yml` and `~/app/.env` are the single source of truth and are **not** mirrored in the repo; the deploy job runs `docker compose pull/up` against whatever's on the box. On the VPS the image must be `ghcr.io/flolec31/stencilia-back:${IMAGE_TAG:-main}`, with a `wget` `/actuator/health` healthcheck and the reverse-proxy sidecar gated on `condition: service_healthy`. GitHub needs secrets `VPS_SSH_KEY`/`VPS_KNOWN_HOSTS` and vars `VPS_HOST`/`VPS_USER`. The README `## Deployment` section has the one-time-setup summary.
